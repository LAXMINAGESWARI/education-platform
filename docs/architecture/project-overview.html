CurioEd

An institution-aware FastAPI backend and product design for a common-curriculum student-evaluation loop: publish shared materials, enroll learners, assess with one mastery quiz per subtopic, and surface four-pillar evidence to students and teachers.

POC live: student study + quiz loop Backend: FastAPI + PostgreSQL / pgvector Client: React web Teacher UI mock; four-pillar / RN deferred
Architecture diagrams Design docs Repository README

1. Purpose & POC thesis

The platform helps educational institutions improve learning outcomes by combining approved curriculum, online learner activity, assessment evidence, and role-scoped insights. AI assistance is grounded in institution-approved content and operates only inside each user’s role, enrollment, and institutional boundaries.

POC thesis. An administrator publishes one shared source curriculum for an AcademicPeriod → Grade → Subject. Every enrolled student opens a private learning directory that reuses those published source versions. After each subtopic, the student completes the same common objective quiz and receives an evaluation across four pillars: marks, anonymized peer context, weak subtopics, and progress over time. Teachers use assigned-class evidence to support students.

Design principles

  • Two directories — SourceCurriculum is shared and immutable after publish; StudentLearningDirectory is private and progress-owned.
  • Common material first — one trusted material and quiz per subtopic before evaluation begins.
  • Learner evaluation first — each increment strengthens study → quiz → four-pillar evidence.
  • Authorization before retrieval — content and AI context require active Grade–Subject enrollment.
  • Facts before interpretation — distinguish source facts, calculated metrics, and later AI wording.
  • No curriculum mutation from analytics — student evidence must not rewrite the common source.
  • Portable infrastructure — local adapters replaceable by production services.

5. Identity, tenancy & authorization

Key decisions

  • One account belongs to exactly one institution.
  • Administrator-provisioned accounts (no self-signup in the POC).
  • Multiple explicitly scoped roles allowed (e.g. multiple teaching assignments).
  • Student access requires both active Grade enrollment and active Grade–Subject enrollment.
  • Auth: backend-managed email/password with access + refresh tokens.
  • Deactivation revokes sessions immediately; records remain for audit.

Authorization order (every protected request)

  1. Authenticated?
  2. User active and session valid?
  3. Resource in user’s institution?
  4. Academic period status permits the action?
  5. Role and explicit scope permit?
  6. For learner resources: Grade + Grade–Subject enrollments?
  7. Resource lifecycle (published / released) permits?
Client-supplied grade, subject, or student identifiers never grant access by themselves. Authorization runs before content lookup and before any AI context assembly.

Period status effects

StatusAdministratorTeacherStudent
PlannedConfigureRead setupNo learner access
ActiveFull configured authorityView assigned evidenceStudy, attempt, view released results
ClosedAudited correctionsMostly read-onlyRead-only history
ArchivedRead-onlyOriginal scope read-onlyOwn history read-only

6. Academic structure & enrollment

Academic periods are first-class. One period is active per institution at a time. Grade 8 Mathematics in 2026–27 is distinct from Grade 8 Mathematics in 2027–28. 

Institution
├── Academic period
│   ├── SourceCurriculum (Grade → Subject → Topic → Subtopic)
│   ├── Grade
│   │   ├── StudentGradeEnrollment
│   │   └── Section (optional reporting group only)
│   ├── StudentSubjectEnrollment (Grade–Subject offering)
│   └── Teaching assignment (Teacher + Grade–Subject ± section)
└── Users / Student profiles

POC decisions

  • Same published material and quiz for every student in a Grade–Subject offering.
  • Sections do not change material or quiz assignment in the POC.
  • Student section transfer not supported in the POC.
  • Timetable retained for later teacher workflows; not required for material/quiz access.
  • Administrators create or copy prior-period Topic/Subtopic templates as new period-scoped records.
Design: academic structure

7. Materials, publication & ingestion

Administrators create folder structure, upload source files under a subtopic, and publish an immutable version. Enrolled students resolve that version by reference. A common mastery quiz may release only after its material is published.

Publication lifecycle

stateDiagram-v2
    [*] --> Draft
    Draft --> Processing: UploadAccepted
    Processing --> Ready: IngestionSucceeds
    Processing --> Failed: IngestionFails
    Failed --> Draft: CorrectAndReupload
    Ready --> Published: AdminPublishes
    Published --> Superseded: NewerVersionPublished
    Published --> Archived
    Superseded --> Archived
  • Draft / processing versions are invisible to students.
  • Publishing a newer version supersedes the previous for new study sessions.
  • Existing progress and attempts keep the exact version the student used.
  • Ingestion: validate → store blob → parse PDF/DOCX/TXT → chunk with metadata → optional embeddings → ready/failed.
  • Uploaded and extracted text are untrusted data—never system instructions.
Design: material lifecycle

8. Assessment — common subtopic mastery quizzes

One common objective mastery quiz per Grade–Subject–Subtopic. Every enrolled student attempts the same published question set (subject to retake policy and attempt windows).

Question types (POC)

TypeMarking
Multiple choiceExact option match
True / falseExact boolean match
MatchingExact mapping match
Short numericNormalized numeric comparison

Every question maps to the parent subtopic and at least one learning outcome (enables struggle analysis).

Attempt lifecycle

stateDiagram-v2
    [*] --> NotStarted
    NotStarted --> InProgress: StartAttempt
    InProgress --> Submitted: StudentSubmits
    InProgress --> Expired: TimerEnds
    Submitted --> Scored: AutoScore
    Expired --> Scored: AutoScoreLockedAnswers
    Scored --> Released: ResultsVisible
    Scored --> Held: AwaitAdminRelease
    Held --> Released: ResultsReleased
    Released --> Invalidated: AuditedCorrection
  • Only one InProgress attempt per student per quiz version at a time.
  • Answers immutable after Submitted / Expired.
  • Retakes create a new attempt; history is retained.
  • Result release: institution default immediate or admin_release.
  • Deferred: adaptive practice, section variants, live AI question authoring, subjective grading.
Design: assessment

9. Analytics — four evaluation pillars

Each scored released attempt writes a versioned EvaluationSnapshot into the student’s private directory. Analytics must not rank students by default, expose classmate identities, or change SourceCurriculum.

1. Marks

Attempt score, percent, pass/mastery flags, attempt history, subject average, completion rate.

2. Peer context

Anonymized percentile/cohort band for the same quiz version. Never names or raw peer marks.

3. Subtopic / outcomes

Outcome scores and struggle flags from tagged answers (default struggle: <50% with ≥2 tagged questions).

4. Progress over time

Score, mastery, and completion trends; retake deltas across successive quizzes.

Evidence model

TypeMeaningExample
Source factImmutable recorded eventScored 21/30 on Linear Equations quiz v1 attempt 1
Calculated metricDeterministic from factsOutcome “inverse operations” correctness 40%
ComparisonRelation to eligible cohortMiddle 50% band for this quiz version

Peer evidence gate

marked_students >= 5
AND marked_students / enrolled_students_at_assessment >= 0.80

If unmet: show personal metrics only; suppress peer conclusions (insufficient evidence).

Default thresholds

  • Mastery: 70%
  • Pass: 50%
Design: analytics

10. Student learning loop

Sign in
  → open private AcademicPeriod / Grade / Subject directory
  → open Topic / Subtopic
  → study administrator-published source material (referenced)
  → take the common mastery quiz for that subtopic
  → receive marks, peer context, weak-subtopic evidence, progress over time
  → continue to the next subtopic

Default progression: next subtopic unlocks after the prior subtopic quiz is submitted. Missing either required enrollment yields an explicit blocked home state with no curriculum leak.

Repository conventions

  • Python via uv (no requirements.txt).
  • Thin HTTP routes; business logic in module services; persistence in models/repositories.
  • Alembic migrations for schema; do not rely on create_all for production.
  • Package layout under src/education_platform/: core, api, db, modules (auth, academics, materials, assessments, rag, assistant), plus workers.
  • Compose stack: PostgreSQL + pgvector only (ingest queue in Postgres; MinIO deferred).
  • Provider-neutral LLM/embedding ports; OpenRouter optional for admin policy assistant LLM stages.
  • Client: React web against the FastAPI OpenAPI / JWT contract (React Native deferred).

13. Implemented today vs designed POC

Implemented today

  • JWT auth for students and administrators; enrollment-gated student access
  • SourceCurriculum seed + StudentLearningDirectory (progress and quiz attempts)
  • Common mastery quizzes with automatic scoring (no answer keys on student APIs)
  • Admin materials browse, curriculum/knowledge PDF ingest, pgvector indexing
  • Admin policy assistant (multi-chat + retrieval; OpenRouter optional for LLM stages)

Designed / not in POC yet

  • Teacher workspace backed by APIs (frontend fixtures only today)
  • Four-pillar evaluation snapshots and teacher class insights
  • Student grounded AI assistant
  • MinIO/S3 object storage and React Native client
  • Full CMS / markdown publish editor beyond PDF ingest

14. Trust boundaries & security

flowchart TB
    subgraph Untrusted[Untrusted]
        Client[Client_requests]
        Uploads[Uploaded_files_extracted_text]
        ModelOut[Model_output]
        PeerRaw[Peer_identities_raw_marks]
    end
    subgraph Trusted[Trusted_server_side]
        AuthZ[AuthN_AuthZ_enrollment_checks]
        Policy[Publication_and_release_policy]
        Scoring[Deterministic_objective_scoring]
        Snapshots[Evaluation_snapshots]
        AnonPeer[Anonymized_peer_bands_only]
    end
    Client --> AuthZ
    Uploads --> Policy
    ModelOut --> Policy
    AuthZ --> Scoring
    Scoring --> Snapshots
    Snapshots --> AnonPeer
    PeerRaw -.->|never_exposed_to_students| AnonPeer
    Snapshots -.->|must_not_mutate| SourceCurriculum[SourceCurriculum]
  1. Client → API — clients untrusted; authz is server-side.
  2. Institution isolation — tenant IDs are never proof of access.
  3. Uploaded files — files and extracted text are untrusted data.
  4. Retrieved text → model — cannot override system/application policy.
  5. Model output — untrusted until schema validation and policy checks; cannot grant access, change scores, or publish curriculum.
  6. Analytics → curriculum — derived insights cannot silently alter SourceCurriculum.
  7. Peer privacy — anonymized aggregates only.
  8. Student directories — never visible across students.

16. Local setup & quality gates

Prerequisites

  • Docker Desktop (PostgreSQL + pgvector via Compose)
  • uv and Python 3.12; Node 18+
  • macOS/Linux: bash + curl; Windows: PowerShell

Bootstrap

# macOS / Linux
./scripts/setup-macos.sh

# Windows PowerShell
./scripts/setup-windows.ps1

docker compose up -d postgres
# wait until healthy
cd backend
uv run alembic upgrade head
# API auto-seeds from docs/curriculum/ when no topics exist
uv run uvicorn education_platform.main:app --reload --host 127.0.0.1 --port 8000

# Frontend (separate terminal)
cd frontend
cp .env.example .env
npm install
npm run dev
# App: http://localhost:5173  |  API docs: http://127.0.0.1:8000/docs

# Demo password demo1234: fatima.almansouri@alnoor.school (admin), meera.krishnan@alnoor.school (teacher), student1@alnoor.school (Adnan, Grade 6), student97@alnoor.school (Aisha Rahman, Grade 8)
# Optional: OPENROUTER_API_KEY in backend/.env for live policy LLM stages
# Optional ingest worker: cd backend && uv run python -m education_platform.workers

Quality checks

cd backend
uv run ruff format --check .
uv run ruff check .
uv run mypy src
uv run pytest

cd frontend
npm test

Project agent rules also require institution/role/enrollment/publication checks before curriculum retrieval, treating uploads and model output as untrusted, and Alembic for schema changes. See the repository README for the full start path.
